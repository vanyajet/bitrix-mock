# ТЗ: Demo CRM Analytics Dashboard (тестовое задание, Bitrix24 + PostgreSQL + Node.js)

## 0. Контекст (прочитай первым)

Это тестовое задание на вакансию Backend-разработчика (Node.js). Заказчик ведёт клиентов в Bitrix24 CRM и хочет дашборды по их данным: лиды, конверсии, реклама, финансы, команда. Примеры его дашбордов:
- Стоматологическая клиника: лиды, разбивка по каждому врачу (сколько лидов пришло, сколько заработал, конверсия), конверсия по источникам рекламы.
- Продажа металлоконструкций: направления (коммерческие помещения, ИЖС и другие), выручка и конверсия по направлениям.

Оценивать будут БЭКЕНД: структуру данных, интеграцию с Bitrix24, синхронизацию, SQL-агрегацию, деплой. Фронтенд - витрина, он тонкий и ничего не считает сам.

Цель: рабочий задеплоенный демо-сервис по публичной ссылке, который можно открыть и потыкать. Максимальная простота и дешевизна деплоя.

Что НЕ делаем: пользователей и регистрацию, админку, анимации, тесты на всё подряд, мультитенантность.

## 1. Архитектура

Один Docker-контейнер (один сервис на хостинге) + внешний PostgreSQL.

```
[Fastify app]
  /mock/rest/...   Mock Bitrix24 REST API (формат реального вебхука)
  /mock/ads/...    Mock рекламного кабинета (расходы по каналам)
  sync worker      node-cron внутри процесса, дёргает Bitrix-клиент
  /api/...         Aggregation API (SQL-агрегаты из Postgres)
  /                раздаёт собранный фронт (static)
[PostgreSQL]       leads, deals, stages, users, ad_spend, sync_runs, sync_state
```

Ключевой принцип: sync-воркер ходит в Bitrix через обычный HTTP-клиент по URL вебхука. Переключатель `BITRIX_MODE=mock|live`:
- `mock`: клиент ходит на собственный `/mock/rest/...` в этом же приложении.
- `live`: клиент ходит на `BITRIX_WEBHOOK_URL` (реальный портал Bitrix24). Код синка не меняется.

## 2. Стек

- Node.js 20, TypeScript (strict), Fastify, zod (валидация входа и env), pino-логи.
- PostgreSQL, драйвер `pg`, миграции простым SQL-раннером (папка `migrations/*.sql`, таблица `schema_migrations`). Без ORM: нужны materialized views и оконные функции.
- Фронт: Vite + React + TypeScript + TanStack Query + Recharts. Стили простые (CSS modules или Tailwind), аккуратный тёмный или светлый UI без излишеств.
- Тесты: vitest, 4-5 тестов (см. раздел 9).
- Docker (multi-stage), docker-compose для локального запуска (app + postgres).

Структура репо:
```
/src
  /bitrix       клиент, типы, retry/backoff, rate limit
  /mock         mock Bitrix + mock ads, сидер (faker, фиксированный seed)
  /sync         воркер, upsert-логика, расписание
  /db           пул, миграции, запросы
  /api          роуты агрегатов, схемы zod, auth
  /config       env
/web            фронт
/migrations
Dockerfile, docker-compose.yml, README.md, .env.example
```

## 3. Mock Bitrix24 REST API

Повторяет формат реального Bitrix24 (вебхук вида `/mock/rest/1/<token>/<method>.json`). Ответ: `{ "result": [...], "next": 50, "total": 1234, "time": {...} }`.

Методы:
- `crm.lead.list`, `crm.deal.list`, `crm.status.list`, `crm.category.list`, `user.get`.
- Пагинация: страница по 50 записей, параметр `start`, поле `next` в ответе (как в реальном API).
- Фильтры: `filter[>DATE_MODIFY]`, `filter[>=DATE_CREATE]`, `filter[SOURCE_ID]`; `select[]`; `order`.
- Проверка токена вебхука, при неверном - 401 в формате Bitrix (`{"error":"...","error_description":"..."}`).
- Имитация лимита: при более 2 запросов в секунду с одного токена отдавать ошибку `QUERY_LIMIT_EXCEEDED` (клиент обязан ретраить с backoff).

Поля лида: `ID, TITLE, STATUS_ID, SOURCE_ID, ASSIGNED_BY_ID, DATE_CREATE, DATE_MODIFY, OPPORTUNITY, CURRENCY_ID, CATEGORY_ID (вертикаль), UF_CRM_SEGMENT`.
Поля сделки: `ID, LEAD_ID, STAGE_ID, CATEGORY_ID, ASSIGNED_BY_ID, OPPORTUNITY, CLOSEDATE, DATE_CREATE, DATE_MODIFY, UF_CRM_SEGMENT`.

Данные хранятся в памяти (сгенерированы сидером при старте, seed фиксирован, чтобы данные были детерминированными). Опционально: раз в минуту mock «изменяет» несколько записей (двигает стадию, обновляет DATE_MODIFY), чтобы инкрементальный синк был виден вживую.

### Две вертикали на одной модели
1. **Стоматология** (CATEGORY_ID=1): сегменты услуг - терапия, имплантация, ортодонтия, гигиена. Менеджеры - 6 врачей/специалистов с разной конверсией (от 18% до 41%) и разным средним чеком.
2. **Металлоконструкции** (CATEGORY_ID=2): сегменты - коммерческие помещения, ИЖС, промышленность, агро. 5 менеджеров. Чек на порядок больше, цикл сделки длиннее.

Источники (SOURCE_ID): `google_ads, yandex_direct, instagram, seo, referral, cold_call` с разным CPL и разным качеством лидов.

Реалистичность (обязательно): 12 месяцев истории, сезонность (стоматология падает летом, металлоконструкции растут весной-осенью), будни/выходные, часть лидов уходит в «не дозвонились» и «отказ», разные конверсии по источникам, рост за год. Объём: порядка 15-25 тыс. лидов суммарно.

Стадии: `NEW, IN_PROGRESS, NO_ANSWER, QUALIFIED, MEETING, WON, LOST`.

## 4. Mock рекламных расходов

В Bitrix24 расходов на рекламу нет: их берут из рекламных кабинетов. Поэтому отдельный mock-эндпоинт `GET /mock/ads/spend?from=&to=&vertical=` возвращает дневные расходы, показы, клики по каналам. Sync подтягивает их в `ad_spend`. В README явно написать, что в проде это Google Ads / Yandex Direct API.

## 5. Sync-воркер

- Расписание: node-cron, каждые 5 минут (интервал из env) + эндпоинт ручного запуска `POST /api/sync/run` (под токеном).
- Инкрементальность: курсор `last_modified` хранится в `sync_state` по каждой сущности. Запрашиваем `filter[>DATE_MODIFY]=cursor`, идём по `next` до конца, курсор двигаем только после успешного коммита батча.
- Первый запуск: full sync постранично (пакетами, не держать всё в памяти).
- Идемпотентность: `INSERT ... ON CONFLICT (bitrix_id) DO UPDATE ... WHERE excluded.date_modify >= table.date_modify`. Повторный прогон не меняет данные.
- Защита от параллельных запусков: `pg_advisory_lock`.
- Отказоустойчивость: retry с экспоненциальным backoff и jitter на сетевые ошибки, 5xx и `QUERY_LIMIT_EXCEEDED`; таймауты; корректное завершение (SIGTERM).
- Журнал: таблица `sync_runs` (started_at, finished_at, status, entity, fetched, upserted, error).
- Удаления: не обрабатываем, в README пометить как known limitation (в проде - события `ONCRMLEADDELETE` или периодическая сверка ID).

## 6. База данных

Таблицы: `users`, `stages`, `leads`, `deals`, `ad_spend`, `sync_runs`, `sync_state`, `schema_migrations`.
- В `leads`/`deals` хранить `bitrix_id` (unique), `vertical`, `segment`, `source`, `stage`, `assigned_user_id`, `amount`, `created_at`, `modified_at`, `closed_at`, `is_won`.
- Индексы под реальные фильтры: `(vertical, created_at)`, `(vertical, source, created_at)`, `(assigned_user_id, created_at)`, частичный индекс по `is_won`.
- Агрегаты: SQL-запросы с `date_trunc`, `FILTER (WHERE ...)`, оконными функциями; тяжёлые срезы (помесячные по источникам и менеджерам) вынести в materialized views, обновлять `REFRESH MATERIALIZED VIEW CONCURRENTLY` после успешного синка.
- Деньги хранить как `numeric(14,2)`, никаких float.

## 7. Aggregation API

Все GET, общие query-параметры: `vertical` (dental|metal), `from`, `to` (ISO даты, дефолт - последние 90 дней), `segment` (опционально). Валидация zod, ошибки в едином формате. Кэш ответов в памяти на 60 секунд (ключ = эндпоинт + параметры), сбрасывается после синка.

- `GET /api/overview` - KPI: лиды, сделки выиграно, конверсия, выручка, средний чек, расходы, CPL, CAC, ROMI; сравнение с предыдущим периодом (дельта %); временной ряд лидов и выручки по неделям.
- `GET /api/marketing` - по каждому источнику: лиды, расход, CPL, клики, конверсия лид-в-сделку, выручка, ROMI; динамика по месяцам.
- `GET /api/funnel` - воронка по стадиям: количество, конверсия между стадиями, потери, среднее время на стадии.
- `GET /api/finance` - выручка по месяцам и сегментам, средний чек, план/факт (план хранится в таблице `plans` или в конфиге сидера), топ сегментов.
- `GET /api/team` - по каждому специалисту: лиды получено, выиграно, выручка, конверсия, средний чек, средняя скорость обработки лида.
- `GET /api/sync/status` - последний прогон, длительность, число обновлённых записей, ошибки, режим (mock/live).
- `POST /api/sync/run` - ручной запуск (под токеном).
- `GET /api/health` - публичный: статус БД и возраст последней успешной синхронизации.

Доступ: демо закрыто простым токеном (`DASHBOARD_TOKEN`), передаётся через header или basic auth (чтобы ссылку можно было открыть в браузере с логином/паролем). `/api/health` открыт. Добавить `@fastify/helmet`, `@fastify/rate-limit`.

## 8. Фронтенд (одна страница с табами)

Табы: **Обзор, Маркетинг, Воронка, Финансы, Команда**. Верхняя панель: переключатель вертикали (Стоматология / Металлоконструкции), выбор периода (7/30/90 дней, год, свой диапазон), фильтр сегмента. Все цифры и графики приходят готовыми с `/api/*`, на фронте только форматирование и отображение.

- Обзор: KPI-карточки с дельтами, график лидов и выручки по неделям.
- Маркетинг: таблица источников (CPL, конверсия, ROMI) + столбчатый график, динамика по месяцам.
- Воронка: горизонтальная воронка с конверсиями между шагами.
- Финансы: выручка по месяцам (stacked по сегментам), план/факт.
- Команда: таблица специалистов с сортировкой, мини-бары конверсии.
- Подвал или боковой блок «Синхронизация»: режим mock/live, время последнего прогона, число обновлённых записей, статус, кнопка «Синхронизировать сейчас».
- Состояния загрузки и ошибок обязательны, адаптивность до планшета.

## 9. Тесты (минимум)

1. Bitrix-клиент: пагинация через `next` собирает все страницы.
2. Bitrix-клиент: ретрай на `QUERY_LIMIT_EXCEEDED` с backoff.
3. Sync: повторный прогон идемпотентен (количество и содержимое строк не меняются).
4. Sync: инкрементальный прогон подтягивает только изменённые записи и двигает курсор.
5. Агрегат: конверсия и CPL на маленьком фиксированном наборе считаются верно.

## 10. Деплой (дёшево и просто)

Цель: одна публичная ссылка. Рекомендуемая схема:
- Приложение: один Docker-сервис на Render (Web Service из Dockerfile, free или минимальный платный план). Альтернативы: Railway, Fly.io, Koyeb.
- База: Neon (бесплатный Postgres) или Supabase, строка подключения в `DATABASE_URL`. Не использовать встроенный бесплатный Postgres Render: он истекает.
- Фронт собирается в Docker-образе и раздаётся тем же Fastify (без отдельного хостинга).
- Миграции и сидирование mock-данных выполняются автоматически при старте (идемпотентно).
- Бесплатный план засыпает при простое, поэтому: `/api/health` для пинга, в README указать про холодный старт (или поставить внешний пинг раз в 10 минут).
- Переменные окружения: `DATABASE_URL, BITRIX_MODE, BITRIX_WEBHOOK_URL, DASHBOARD_TOKEN, SYNC_INTERVAL_MIN, PORT, NODE_ENV`.
- Дополнительно в README: секция «Продакшен на VPS» - systemd/PM2 или Docker Compose, пример Nginx reverse proxy с HTTPS (certbot), бэкап Postgres через `pg_dump` по cron, безопасная выкатка обновлений (миграции перед стартом, healthcheck, откат). Это показывает Linux/Nginx/PM2 без реального сервера.

## 12. Критерии готовности

- `docker compose up` поднимает всё, через минуту на дашборде есть данные.
- Публичная ссылка работает, все 5 табов и оба переключателя вертикали отдают данные.
- Тумблер `BITRIX_MODE=live` не требует правок кода.
- Повторный синк ничего не дублирует, статус синка виден в UI и в `/api/sync/status`.
- Агрегаты считаются в SQL, на фронте нет бизнес-расчётов.
- Тесты проходят, `tsc --noEmit` и линтер без ошибок.
- README позволяет другому разработчику запустить и задеплоить без вопросов.
