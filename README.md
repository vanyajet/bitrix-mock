# CRM Analytics: Bitrix24 → PostgreSQL → дашборд

Демо-сервис аналитики по данным Bitrix24 CRM: лиды, конверсии, реклама, финансы, команда.
Две вертикали на одной модели: **стоматология** (врачи, услуги) и **металлоконструкции** (направления, длинный цикл сделки).

- Синхронизация с Bitrix24 через обычный REST-вебхук: инкрементально, идемпотентно, с ретраями и защитой от параллельных запусков.
- Все метрики считаются в PostgreSQL (CTE, `FILTER`, оконные функции, materialized views); фронтенд только отображает.
- `BITRIX_MODE=mock|live`: встроенный эмулятор Bitrix24 или реальный портал. Код синка в обоих режимах один и тот же.

## Быстрый старт

```bash
docker compose up --build
```

Откройте <http://localhost:3000> и войдите: логин любой, пароль `demo-dashboard-token`.
Через ~40 секунд после старта на дашборде есть данные: первый полный синк ~136 тыс. записей
(лиды, сделки, история стадий, расходы) занимает около 30 секунд.

Что происходит при старте:
1. миграции из `migrations/*.sql` (идемпотентно, под advisory lock);
2. сидирование планов выручки (только недостающие строки);
3. генерация mock-портала в памяти (детерминированно, seed + дата);
4. первый синк, дальше по расписанию каждые `SYNC_INTERVAL_MIN` минут.

Повторный `docker compose up` данные не дублирует: синк инкрементальный, upsert идемпотентный.

## Синхронизация

| Сущность | Метод Bitrix24 | Курсор | Запись |
|---|---|---|---|
| Справочники | `user.get`, `crm.status.list`, `crm.category.list`, `crm.lead.userfield.list`, `crm.deal.userfield.list` | - (целиком, маленькие) | upsert |
| Лиды | `crm.lead.list` | `DATE_MODIFY` | upsert |
| Сделки | `crm.deal.list` | `DATE_MODIFY` | upsert |
| История стадий лидов / сделок | `crm.stagehistory.list` (`entityTypeId` 1 / 2) | `CREATED_TIME` | insert, записи неизменяемы |
| Расходы на рекламу | `GET /mock/ads/spend` | дата; последние 3 дня перезапрашиваются | upsert |

- **Инкрементальность.** `filter[>DATE_MODIFY] = cursor − SYNC_CURSOR_OVERLAP_SEC`, `order: DATE_MODIFY ASC, ID ASC`, проход по `next` до конца.
  Каждая страница (или пачка страниц) пишется в одной транзакции **вместе со сдвигом курсора**: курсор не убегает вперёд незаписанных данных.
  Небольшое перекрытие окна страхует от записей с той же секундой `DATE_MODIFY`; повторно прочитанные записи ничего не меняют.
- **Первый запуск** = полный синк постранично, пачки коммитятся сразу, всё в памяти не держится.
  Лимит Bitrix 2 запроса в секунду при 50 записях на страницу означал бы ~17 минут на 100 тыс. записей,
  поэтому после первой страницы (когда известен `total`) остальные запрашиваются через **`batch`**: до 50 страниц за один HTTP-запрос.
- **Идемпотентность.** `INSERT ... ON CONFLICT (bitrix_id) DO UPDATE ... WHERE excluded.modified_at >= t.modified_at AND (...) IS DISTINCT FROM (...)`:
  старые версии не затирают новые, а неизменившиеся строки не переписываются. Поэтому повторный прогон показывает `upserted = 0`.
  Это проверяет тест, и это видно в UI. Дубликаты внутри пачки (сдвиг offset-пагинации) схлопываются до записи.
- **Параллельные запуски.** `pg_try_advisory_lock` на отдельном соединении: cron, ручной запуск и второй инстанс не пересекаются.
  Внутри процесса повторный запуск сразу получает `409 SYNC_IN_PROGRESS`.
- **Отказоустойчивость.** Ретраи с экспоненциальным backoff и jitter на сетевые ошибки, таймауты, 5xx/429 и `QUERY_LIMIT_EXCEEDED`;
  клиентский rate limiter держит интервал между запросами; у каждого запроса таймаут.
  По SIGTERM текущая пачка дописывается, прогон помечается `aborted`, соединения закрываются.
  Прогоны, оборванные падением процесса, закрываются при следующем старте синка.
- **Журнал.** `sync_runs`: строка на сущность в рамках `run_id` (`started_at`, `finished_at`, `status`, `fetched`, `upserted`, `error`).
- **После успешного прогона** - `REFRESH MATERIALIZED VIEW CONCURRENTLY` (чтение не блокируется) и сброс кэша API.

## Mock Bitrix24 и данные

Mock повторяет **формат реального портала**, чтобы режим `live` работал без правок кода:

- вебхук `/mock/rest/1/<token>/<method>.json`, `GET` или `POST` (JSON или form), параметры в стиле Bitrix (`filter[>DATE_MODIFY]`, `select[]`, `order[ID]`);
- ответ `{ "result": [...], "next": 50, "total": 1234, "time": {...} }`, страницы по 50;
- фильтры с операторами `>`, `>=`, `<`, `<=`, `!`, `@`, `%`, `select` (`*`, `UF_*`), `order`;
- числа приходят строками, деньги `"15000.00"`, даты `2026-10-26T12:30:00+03:00`;
- реальные значения: статусы лидов из `crm.status.list` (`ENTITY_ID=STATUS`: `NEW`, `IN_PROCESS`, `CONVERTED`, `JUNK`, `UC_NOANSWER`),
  стадии сделок с префиксом воронки (`C1:NEW`, `C1:PREPARATION`, `C2:PREPAYMENT_INVOICE`, `C1:WON`, `C1:LOSE`) и `SEMANTICS`;
  списочное поле `UF_CRM_SEGMENT` отдаёт **ID значения**, подписи берутся из `crm.*.userfield.list`, а у лидов и сделок ID разные - как в жизни;
- неверный токен → `401 {"error":"INVALID_CREDENTIALS",...}`; больше 2 запросов в секунду на токен → `503 {"error":"QUERY_LIMIT_EXCEEDED"}`;
- `batch` с `halt`, а пустые `result_error` отдаются как `[]` - PHP-особенность, которую клиент обязан переживать.

**Данные.** Генератор детерминированный: день генерируется из `seed + дата`, а все переходы лида
(взят в работу → не дозвонились / отказ / сконвертирован → встреча → оплата) рассчитываются сразу.
API отдаёт **состояние на текущий момент**, поэтому портал «живёт» без таймеров: приходят новые лиды, менеджеры двигают стадии,
сделки закрываются. Инкрементальный синк каждые 5 минут видит реальные изменения.
ID выдаются по порядку создания, как автоинкремент Bitrix, и одинаковы после рестарта (история начинается с фиксированной даты 2025-07-01).

- ~20 тыс. лидов, ~10 тыс. сделок, ~87 тыс. записей истории стадий, 16 месяцев истории;
- сезонность: стоматология проседает летом и в январские праздники, металлоконструкции растут весной–осенью; будни/выходные, часы суток, рост +32% в год;
- 6 врачей с конверсией 18–41% и разным чеком, 5 менеджеров по металлоконструкциям; специализация по сегментам;
- источники `google_ads`, `yandex_direct`, `instagram`, `seo`, `referral`, `cold_call` с разной долей, CPL и качеством лидов;
- часть лидов уходит в «не дозвонились» и «отказ», чек и цикл сделки в металле на порядок больше.

**Расходы на рекламу** в Bitrix24 не хранятся - их берут из рекламных кабинетов.
Здесь это `GET /mock/ads/spend?from=&to=&vertical=` (Bearer-токен, окно до 92 дней): дневные расходы, показы и клики по каналам и кампаниям,
кампания привязана к сегменту. **В продакшене это Google Ads API и Yandex Direct Reports API**:
адаптеры приводят ответ к тем же строкам `ad_spend`, сегмент определяется по названию кампании или UTM.

## Переключение на реальный Bitrix24

1. В портале: **Приложения → Разработчикам → Другое → Входящий вебхук**.
   Права: **CRM** (`crm`) и **Пользователи** (`user`). Скопируйте URL вида `https://example.bitrix24.ru/rest/1/abc123xyz/`.
2. Переменные окружения:
   ```env
   BITRIX_MODE=live
   BITRIX_WEBHOOK_URL=https://example.bitrix24.ru/rest/1/abc123xyz/
   ```
3. Настройте маппинг портала на модель дашборда (код не меняется):

   | Переменная | Назначение | По умолчанию |
   |---|---|---|
   | `BITRIX_CATEGORY_VERTICALS` | воронка сделки (`CATEGORY_ID`) → вертикаль | `1:dental,2:metal` |
   | `BITRIX_DEPARTMENT_VERTICALS` | отдел сотрудника (`UF_DEPARTMENT`) → вертикаль; используется и для лидов | `10:dental,20:metal` |
   | `BITRIX_LEAD_VERTICAL_FIELD` / `BITRIX_LEAD_VERTICALS` | поле лида с вертикалью и его значения (у реальных лидов нет воронок, обычно это UF-поле) | `CATEGORY_ID` / `1:dental,2:metal` |
   | `BITRIX_DEFAULT_VERTICAL` | вертикаль, если ничего не подошло (портал одного бизнеса) | - |
   | `BITRIX_SEGMENT_FIELD` | списочное поле сегмента/направления, например `UF_CRM_1712345678` | `UF_CRM_SEGMENT` |
   | `BITRIX_STAGE_MAP` | ручной маппинг нестандартных статусов на канонические стадии | - |

   Пример: `BITRIX_STAGE_MAP={"UC_CALLBACK":"IN_PROGRESS","C3:CONTRACT":"MEETING"}`.
   Ключ - полный ID или ID без префикса воронки. Стандартные коды Bitrix и семантика (успех/провал) маппятся автоматически.
4. Перезапустите сервис: первый прогон загрузит портал целиком, дальше - инкрементально.

В `live` mock-эндпоинты не регистрируются. Расходы на рекламу по умолчанию выключены (`ADS_ENABLED`): для реального портала нужен адаптер кабинета.
Планы выручки заполняются в таблице `plans`, например:
`INSERT INTO plans (vertical, segment, month, revenue_plan) VALUES ('dental', 'Имплантация', '2026-11-01', 4500000);`
Записи без определимой вертикали пропускаются и считаются в логе синка (`skipped`).

## Маппинг полей Bitrix24 → БД

**Лид** (`crm.lead.list` → `leads`)

| Bitrix24 | БД | Примечание |
|---|---|---|
| `ID` | `bitrix_id` (PK) | |
| `TITLE` | `title` | |
| `STATUS_ID` | `bitrix_status_id`, `stage` | каноническая стадия через `crm.status.list` + семантику + `BITRIX_STAGE_MAP` |
| семантика статуса (`SEMANTICS` / `STATUS_SEMANTIC_ID`) | `is_won`, `closed_at` | `S` - лид сконвертирован; `closed_at` = `DATE_CLOSED` для финальных статусов |
| `SOURCE_ID` | `source` | названия источников - в `sources` из `crm.status.list` (`ENTITY_ID=SOURCE`) |
| `ASSIGNED_BY_ID` | `assigned_user_id` | |
| `DATE_CREATE` / `DATE_MODIFY` | `created_at` / `modified_at` | `DATE_MODIFY` - курсор синка |
| `OPPORTUNITY`, `CURRENCY_ID` | `amount numeric(14,2)`, `currency` | строка → numeric без float |
| `CATEGORY_ID` (или `BITRIX_LEAD_VERTICAL_FIELD`) | `vertical` | фолбэк: отдел ответственного → `BITRIX_DEFAULT_VERTICAL` |
| `UF_CRM_SEGMENT` (ID значения) | `segment` | подпись из `crm.lead.userfield.list` |

**Сделка** (`crm.deal.list` → `deals`)

| Bitrix24 | БД | Примечание |
|---|---|---|
| `ID`, `LEAD_ID`, `TITLE` | `bitrix_id`, `lead_id`, `title` | |
| `STAGE_ID` (`C1:WON`) | `bitrix_stage_id`, `stage` | префикс воронки отбрасывается при маппинге |
| `CATEGORY_ID` | `category_id`, `vertical` | `BITRIX_CATEGORY_VERTICALS` |
| семантика стадии | `is_won` | `S` - выигрыш |
| `CLOSED`, `CLOSEDATE` | `closed_at` | для закрытых сделок; выручка считается по этой дате |
| `SOURCE_ID`, `ASSIGNED_BY_ID`, `OPPORTUNITY`, `CURRENCY_ID`, `DATE_CREATE`, `DATE_MODIFY` | `source`, `assigned_user_id`, `amount`, `currency`, `created_at`, `modified_at` | |
| `UF_CRM_SEGMENT` | `segment` | подпись из `crm.deal.userfield.list` |

**Остальное**

| Bitrix24 | БД |
|---|---|
| `crm.stagehistory.list`: `ID`, `OWNER_ID`, `TYPE_ID`, `STATUS_ID`/`STAGE_ID`, `CATEGORY_ID`, `CREATED_TIME` | `stage_history` (`bitrix_id`, `owner_id`, `type_id`, `bitrix_stage_id` + `stage`, `category_id`, `created_at`) |
| `user.get`: `ID`, `NAME` + `LAST_NAME`, `WORK_POSITION`, `UF_DEPARTMENT`, `ACTIVE` | `users` (`bitrix_id`, `name`, `position`, `vertical`, `active`) |
| `crm.status.list`: `STATUS_ID`, `NAME`, `SORT`, `CATEGORY_ID`, `SEMANTICS` / `EXTRA.SEMANTICS` | `stages` (+ канонический `stage`), `sources` |
| `crm.category.list` (`entityTypeId=2`): `id`, `name` | `categories` |

**Канонические стадии** (из ТЗ) и стандартные коды Bitrix:

| Стадия | Лид | Сделка |
|---|---|---|
| `NEW` | `NEW` | - |
| `IN_PROGRESS` | `IN_PROCESS`, прочие «в работе» | - |
| `NO_ANSWER` | `*NOANSWER*` | - |
| `QUALIFIED` | `PROCESSED`, `CONVERTED` | `NEW` (первая стадия воронки) |
| `MEETING` | - | `PREPARATION`, `PREPAYMENT_INVOICE`, `EXECUTING`, `FINAL_INVOICE`, прочие «в работе» |
| `WON` | - | `WON` / семантика успеха |
| `LOST` | `JUNK`, прочие провальные | `LOSE`, `APOLOGY` / семантика провала |

## Aggregation API

Все аналитические эндпоинты - `GET`. Параметры: `vertical` (`dental` | `metal`, по умолчанию `dental`),
`from`, `to` (`YYYY-MM-DD`, включительно; по умолчанию последние 90 дней), `segment` (необязательный).
Ошибки возвращаются в едином формате `{ "error": { "code", "message", "details?" } }`. Ответы кэшируются на 60 секунд
(заголовок `X-Cache: HIT|MISS`), кэш сбрасывается после синка.

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /api/overview` | KPI: лиды, выигранные сделки, конверсия, выручка, средний чек, расходы, CPL, CAC, выручка с лидов периода, ROMI; дельты к предыдущему периоду той же длины; недельный ряд лидов и выручки |
| `GET /api/marketing` | по источникам: лиды, доля, расход, CPL, CPC, CTR, лид→сделка, лид→продажа, CAC, выручка, ROMI + итог; помесячно лиды по источникам и CPL (из MV) |
| `GET /api/funnel` | шаги воронки: сколько дошло, конверсия от предыдущего шага и от входа, потери (не дозвонились / отказ), в работе, среднее время на стадии |
| `GET /api/finance` | выручка, сделки, средний чек, план за период (пропорционально дням) и выполнение; выручка по месяцам и сегментам; план/факт по месяцам с накопительными суммами; топ сегментов |
| `GET /api/team` | по специалисту: лиды, конверсия, выиграно, выручка, доля, средний чек, скорость реакции на лид (медиана и среднее), доля «не дозвонились»; выручка по месяцам |
| `GET /api/meta` | вертикали и их сегменты, режим, часовой пояс |
| `GET /api/sync/status` | последний прогон по сущностям, длительность, обновлено записей, ошибки, режим, следующий запуск, предыдущие прогоны, курсоры |
| `POST /api/sync/run` | ручной запуск: `202` сразу; `?wait=true` - дождаться результата; `?full=true` - перечитать всё. `409`, если синк уже идёт |
| `GET /api/health` | **публичный**: статус БД и возраст последней успешной синхронизации |

Доступ: `DASHBOARD_TOKEN` в заголовке `Authorization: Bearer <token>`, `X-Dashboard-Token: <token>`
или Basic auth (логин любой, пароль = токен). Basic закрывает и статику, поэтому ссылку можно открыть в браузере -
появится окно логина. Работает и вариант `https://demo:<token>@host/`.

```bash
curl -u demo:demo-dashboard-token 'http://localhost:3000/api/marketing?vertical=metal&from=2026-01-01&to=2026-06-30'
curl -X POST -H 'X-Dashboard-Token: demo-dashboard-token' 'http://localhost:3000/api/sync/run?wait=true'
```

Защита: `@fastify/helmet` (CSP и др.), `@fastify/rate-limit` на `/api` (300 в минуту, ручной синк 6 в минуту),
сравнение токена за постоянное время.

## Принятые решения

- **Атрибуция метрик.** Конверсия, CPL, CAC и ROMI считаются по **когорте лидов, созданных в периоде**: что из них выросло к текущему моменту.
  Выручка, выигранные сделки и средний чек - **по дате закрытия сделки**, как это видит финансист.
  Для металлоконструкций с циклом 1–3 месяца это заметно: в свежих периодах ROMI ниже, потому что сделки ещё не закрылись. В UI есть подсказки.
- **Форматы реального Bitrix24 + маппинг**, а не упрощённые значения из ТЗ: иначе переключение на `live` сломало бы синк.
  Имена полей из ТЗ сохранены (`CATEGORY_ID` у лида в mock - как в ТЗ; в реальном портале его нет, для этого есть фолбэки).
- **`crm.stagehistory.list` и таблица `stage_history`** добавлены сверх списка методов ТЗ.
  Без истории переходов честно не посчитать «среднее время на стадии» и «скорость обработки лида».
- **`batch` для полной загрузки** - иначе первый синк при лимите 2 запроса в секунду шёл бы ~17 минут.
- **Materialized views** - помесячные срезы по источникам (`mv_source_monthly`, вместе с расходами) и по менеджерам и сегментам (`mv_manager_monthly`).
  Срезы за произвольный период считаются по базовым таблицам с индексами под фильтры: `(vertical, created_at)`,
  `(vertical, source, created_at)`, `(assigned_user_id, created_at)`, частичный по `is_won`.
  Помесячная динамика показывает полные месяцы, пересекающие период.
- **Воронка** строится по самой дальней стадии, до которой дошёл лид (по истории лида и его сделки), а не по текущему статусу.
  Подряд идущие стадии Bitrix с одной канонической стадией склеиваются при подсчёте времени на стадии.
- **Часовой пояс бизнеса** (`APP_TZ`, по умолчанию `Europe/Moscow`) задаётся сессии БД при подключении:
  недели, месяцы и границы периода считаются в нём.
- **Деньги** - `numeric(14,2)` в БД; из Bitrix строка идёт до Postgres без float. В JSON агрегаты отдаются числом.
- **Планы выручки** - таблица `plans`. В mock-режиме сидируются из той же модели, что и данные (с учётом цикла сделки),
  и не перезаписываются при рестарте.
- **Node.js 24 LTS** вместо 20 из ТЗ: поддержка Node 20 закончилась 30.04.2026.
- **UI на русском, тёмная и светлая темы** по системной настройке. Палитра графиков проверена на различимость при дальтонизме,
  цвет закреплён за сущностью (источник, сегмент, сотрудник), а не за местом в рейтинге. Две метрики разного масштаба -
  два графика, а не две оси Y. Анимации отключены (ТЗ).

## Ограничения и следующие шаги

- **Удаления не обрабатываются**: удалённый в Bitrix лид остаётся в БД.
  В проде - обработчик событий `ONCRMLEADDELETE` / `ONCRMDEALDELETE` или периодическая сверка списков ID.
- **Поллинг вместо событий.** Следующий шаг - исходящие вебхуки Bitrix (`ONCRMLEADUPDATE`, `ONCRMDEALUPDATE`) → очередь →
  точечная дозагрузка. Поллинг остаётся как сверка.
- **Offset-пагинация Bitrix.** Если запись меняется во время долгого полного синка, страницы сдвигаются и соседняя запись может быть пропущена.
  Смягчают это перекрытие окна курсора, дедупликация и идемпотентный `POST /api/sync/run?full=true`.
  Надёжнее для больших порталов - keyset-пагинация `filter[>ID]` + `start=-1`.
- **Расходы на рекламу** - mock. Нужны адаптеры Google Ads / Yandex Direct; сопоставление кампания → сегмент по неймингу или UTM.
- **Одна валюта** (RUB); для мультивалютности нужна таблица курсов.
- **Сегмент хранится подписью** значения списка: переименование значения в Bitrix разделит историю.
  Можно хранить ID значения и подтягивать подпись при выдаче.
- **Кэш и rate limit - в памяти процесса.** Для нескольких инстансов - Redis.
- **Нужно прямое подключение к Postgres** (не PgBouncer в transaction mode): синк держит session-level advisory lock,
  а часовой пояс задаётся на сессию. У Neon - строка подключения **без** `-pooler`.
- Нет пользователей, ролей и мультитенантности - один токен на демо (по ТЗ).

## Деплой: Render + Neon

Стоимость - 0 ₽: бесплатный Web Service на Render и бесплатный Postgres на Neon.
Встроенный бесплатный Postgres Render не используется - он истекает.

1. **Neon** (<https://neon.tech>): создайте проект (регион поближе к Render, например `AWS Europe Central (Frankfurt)`).
   В **Connect** выключите **Connection pooling** и скопируйте прямую строку подключения:
   `postgresql://<user>:<password>@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require` - в хосте не должно быть `-pooler`.
2. **GitHub**: запушьте репозиторий.
3. **Render** (<https://render.com>): **New → Blueprint** → выберите репозиторий. Render прочитает `render.yaml`:
   Docker web service, health check `/api/health`, переменные окружения.
   Введите `DATABASE_URL` из Neon. `DASHBOARD_TOKEN`, `MOCK_WEBHOOK_TOKEN` и `ADS_API_TOKEN` сгенерируются сами.
   Пароль от дашборда - значение `DASHBOARD_TOKEN` в **Environment**.
   Без Blueprint: **New → Web Service → Docker**, те же переменные, health check path `/api/health`.
4. После деплоя откройте `https://<service>.onrender.com`. Миграции, сидирование и первый синк выполнятся сами;
   данные появятся примерно через минуту (бесплатный инстанс медленнее ноутбука).

`PORT` Render задаёт сам - приложение его читает. Фронт собирается в том же Docker-образе и раздаётся Fastify, отдельный хостинг не нужен.

**Холодный старт.** Бесплатный инстанс Render засыпает после 15 минут без входящих запросов.
Первый запрос будит его ~30–60 секунд, затем инкрементальный синк догоняет изменения. Cron внутри процесса сон не предотвращает.
Внешний пинг `/api/health` раз в 10 минут (cron-job.org, UptimeRobot) держит сервис бодрым, но тогда синк каждые 5 минут
не даёт Neon уснуть (он засыпает после 5 минут простоя), и бесплатного лимита Neon (~100 CU-часов в месяц) хватит примерно на 2–3 недели.
Если пинг нужен - поставьте `SYNC_INTERVAL_MIN=15` или больше. Для показа ревьюеру проще принять холодный старт.

## Продакшен на VPS

Примеры в `deploy/`:

- **Docker Compose** - `deploy/docker-compose.prod.yml`: приложение и Postgres, приложение слушает только `127.0.0.1:3000`.
  Секреты лежат в `/etc/crm-analytics.env` (`POSTGRES_PASSWORD`, `DASHBOARD_TOKEN`, `BITRIX_MODE`, `BITRIX_WEBHOOK_URL`).
- **Без Docker** - `deploy/crm-analytics.service` (systemd): Node 24 + собранный `dist/`, миграции в `ExecStartPre`,
  `Restart=on-failure`, SIGTERM с таймаутом 30 с. Аналог на PM2:
  `pm2 start dist/index.js --name crm-analytics --kill-timeout 30000 && pm2 save && pm2 startup`.
- **Nginx + HTTPS** - `deploy/nginx.conf`: reverse proxy с `X-Forwarded-*` (Fastify запущен с `trustProxy`), gzip,
  увеличенный таймаут для ручного синка. Сертификат:
  ```bash
  apt install nginx certbot python3-certbot-nginx
  cp deploy/nginx.conf /etc/nginx/sites-available/crm-analytics && ln -s ../sites-available/crm-analytics /etc/nginx/sites-enabled/
  certbot --nginx -d crm.example.com      # выпуск и автопродление (systemd timer certbot.timer)
  nginx -t && systemctl reload nginx
  ```
- **Бэкап** - `deploy/backup.sh`: `pg_dump | gzip`, проверка архива, ротация 14 дней. Запуск по cron:
  `15 3 * * * /opt/crm-analytics/deploy/backup.sh >> /var/log/crm-backup.log 2>&1`.
  Копию стоит уносить с сервера (`rclone` / S3). Восстановление описано в комментарии скрипта.
- **Безопасная выкатка** - `deploy/deploy.sh <git-ref>`:
  1. сборка образа с тегом коммита (предыдущий образ остаётся для отката);
  2. **миграции до старта** новой версии (`node dist/db/migrate-cli.js`, под advisory lock);
  3. перезапуск с graceful shutdown (текущая пачка синка дописывается);
  4. ожидание `GET /api/health`;
  5. при неудаче - **откат** на предыдущий образ.

  Миграции пишутся по схеме expand/contract (сначала добавить, удалить старое - отдельным релизом), поэтому предыдущая версия работает на новой схеме.

## Разработка и тесты

```bash
npm install
cp .env.example .env
docker compose up -d db          # Postgres для разработки и тестов
npm run dev                      # бэкенд на :3000 (tsx watch)
npm run dev:web                  # фронт на :5173, proxy /api подставляет токен из .env

npm test                         # vitest (нужен Postgres: создаёт базу crm_test, TEST_DATABASE_URL переопределяет)
npm run typecheck                # tsc --noEmit для бэкенда и фронта
npm run lint                     # eslint
npm run build                    # dist/ + web/dist/
```

Тесты (`test/`):

1. **Bitrix-клиент: пагинация через `next`** собирает все страницы; догрузка через `batch` сохраняет `+` в курсоре-дате.
2. **Bitrix-клиент: ретрай на `QUERY_LIMIT_EXCEEDED`** с экспоненциальным backoff (проверяются задержки), без ретраев на 401, сдаётся после `maxRetries`.
3. **Sync: повторный прогон идемпотентен** - и инкрементальный, и полный (`full=true`): `upserted = 0`, md5-отпечатки таблиц не меняются.
4. **Sync: инкрементальный прогон** после «суток жизни» портала забирает ровно изменившиеся лиды (больше страницы, через `batch` с курсором),
   двигает курсор на максимальный `DATE_MODIFY`, не трогает неизменившиеся строки; параллельный запуск отклоняется.
5. **Агрегаты** на маленьком фиксированном наборе: конверсия, CPL, CAC, ROMI, метрики по источникам, воронка,
   граница периода по часовому поясу, отсечение шума (другая вертикаль, лид вне периода); те же числа через HTTP API с авторизацией.

Синк в тестах ходит в mock Bitrix24 по настоящему HTTP, данные пишутся в настоящий Postgres.
